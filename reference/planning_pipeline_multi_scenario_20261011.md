# K-City 다른 rosbag 시나리오 종단 재생 비교 (2026-10-11)

기본 시나리오의 PNG·CSV 10쌍과 대응 재생 조건 JSON만 각 `result`에 보관한다. 진단 CSV·로그·재생 기록은 [압축 보관 파일](../../251231_KCity_ori/planning_aa_result_diagnostics_20261011.tar.gz)에 묶었고, 핵심 대조 입력만 `reference/data`에 별도로 남겼다. 향후 진단 재생 결과는 `251231_KCity_ori/planning_aa_diagnostics/`에 생성되며, `--plot-diagnostics`를 지정한 경우에만 진단 PNG도 만든다.

## 방법과 범위

`reference/run_planning_pipeline_scenario_plots.py`로 `251231_KCity_ori`의 10개 bag을 처리했다. 10개 bag의 전체 프레임을 route부터 planning-aa 최종 validator까지 독립 재생했다. 기본 결과에는 원본 Planning 출력인 `/planning/scenario_planning/max_velocity`도 입력으로 넣지 않았다. 기록된 행동 경로 수신 시각은 계산 시계로만 사용했다. 각 프레임의 기록된 차량 위치에 원본 최종 궤적과 planning-aa 최종 궤적을 투영해 속도, 경로상 가속도, 첫 0 m/s 점까지의 거리를 그렸다. 회색 실제 차량 속도와 제어 가속도는 계산 결과가 아니라 기록된 주행 문맥이다. 첫 0 m/s 점은 경로의 끝점일 수도 있으므로 장애물 정지점과 동일시하면 안 된다.

재생 명령은 원본 분기와 대조한 K-City 입력 설정 `--simulation`과 `--crosswalk-auto-activation`을 명시적으로 전달한다. 이 두 설정은 실제 환경의 기본 동작을 바꾸지 않으며, 다른 배포 기록에서는 해당 노드 파라미터와 RTC 설정을 별도로 확인해야 한다.

현재 CSV 재생은 원본 순항 디버그 RSS 값에서 역산한 안전거리 마진 `6m`와 저장소 launch의 차로 밖 예측 경로 검사 수 `3`을 명시한다. 6m는 순항 활성 기록이 있는 HPC cutinout·blocking, IPC cutinout에서 확인됐으며, 실행 당시 파라미터 덤프는 없다. 각 CSV 옆의 `.replay.json`은 재생 명령·runner와 bag의 수정 시각을 기록한다. `--reuse-csv`는 이 조건이 같을 때만 CSV를 재사용한다. 후보 선택 시각의 잔여 차이는 [순항 후보 경계 감사](obstacle_cruise_candidate_boundary_20261011.md)에 기록했다.

원본 `signals_merged_*.xlsx`가 있는 5개 신규 시나리오는 원본 그림의 시간 원점과 같은 시계에 그래프를 맞췄다. 원본 그림이 없는 4개는 첫 planning 수신 시각을 0초로 썼다. 원본 그림의 차량 속도와 bag odometry를 보간 비교한 결과 시간 정렬 후 속도 차이 중앙값은 모두 0 m/s였다. 계산이 빠진 프레임도 보존하도록 재생기의 `--allow-incomplete-calculation`을 사용했다. 따라서 스크립트 종료 코드 0은 전체 프레임 동등성을 뜻하지 않는다.

## 지역 route 연결 수정

최초 재생에서는 HPC blocking, HPC pedestrian2, IPC pedestrian의 모든 프레임에서 행동 경로부터 최종 출력까지 비었다. 세 bag의 선호 lanelet 경계 간격이 각각 `35 → 15850: 3.54m`, `16927 → 16953: 3.31m`, `24843 → 24846: 3.31m`로 기존 2m 접점 검사를 넘었기 때문이다. 원본 `RouteHandler`처럼 현재 route 차로에서 연결 가능한 지역 차로열을 만들고, 후속 차로가 없으면 현재까지 만든 경로를 유지하도록 수정했다. 가장 가까운 route 차로는 원본의 차로 다각형 거리·방향 우선 기준으로 고른다. 목표 차로가 지역 경로에 없더라도 원본 고정 목표점 처리처럼 경로 끝점의 속도를 0으로 한다. 이 수정만 적용했을 때 세 bag의 독립 최종 출력은 각각 517/573, 453/517, 417/459프레임으로 늘었다. 후속 수정까지 적용한 현재 결과는 각 bag의 전체 프레임에 최종 출력이 있다.

초기 재생에서는 HPC cutinout의 95백분위 오차가 4.754m/s였고, 약 21~25초 구간에서 planning-aa가 원본보다 급하게 감속했다. 아래 순항 속도 제한 연결 후 4m 기본 마진 재생의 95백분위는 1.528m/s였으며, 기록에서 확인한 6m 마진의 현재 재생은 1.735m/s다. HPC runout의 16프레임과 HPC stopline2의 43프레임에서 나타났던 독립 최종 궤적 누락은 최종 스무더의 한 점 경로·QP 실패 처리 수정 뒤 사라졌다.

### IPC pedestrian 원인 세부 분석

첫 프레임의 route 선호 lanelet은 `24843 → 24846 → 24739 → 24978`이지만, 지도에서 `24843 → 24846` 중심선 간격은 3.315m이고 routing graph의 후속 관계도 없다. 실제 연결은 `24843 → 24847`이며 접점 간격은 0m다. 원본 첫 행동 경로는 바로 이 두 lanelet의 34점, 약 60.64m로 끝난다. 수정 전 `onRouteFrame`은 네 구간의 선호 lanelet을 먼저 이어 붙이다가 2m 접점 검사에서 무효를 반환했다. 수정 후 첫 프레임에는 독립 경로 33점이 생성되고 시작점·끝점이 원본과 같다.

수정 전 실험적 route 연결 옵션은 후속 `24847 → 24739`를 전체 route에서 반드시 찾았다. 이 둘은 3.327m 옆 차로 간격이고 routing graph의 직접 후속 관계가 없다. 원본 `RouteHandler::getLaneletSequenceAfter`는 후속 차로가 없으면 이미 모은 지역 경로를 유지한다. 기록된 행동 경로 메시지의 lanelet ID 구간은 0~108번 `24843,24847`, 109~165번에는 `24846`이 추가되고, 358~465번에는 `24739,24978`만 남는다. 행동 경로의 점 수·점별 위치·속도가 원본과 1mm·0.001m/s 안에서 일치한 프레임은 현재도 44/459개다. 보행자 감속 동등성은 아직 확인되지 않았다.

### 차로 변경과 최종 평활화의 후속 수정

기존 자동 차로 변경 판정은 첫 route 구간의 선호 lanelet만 조사했다. 이 bag에서는 첫 구간 `24843` 뒤에 연결된 `24847`에서 다음 구간의 선호 차로 `24846`으로 옮겨야 하므로, 첫 구간만 보면 변경 후보가 누락된다. 원본 `RouteHandler::getLaneChangeTarget`은 현재 차로열을 순서대로 살피며 선호 차로로 가는 이웃 차로를 찾고, `NormalLaneChange::isLaneChangeRequired`는 목표 차로 시작까지의 거리와 최대 준비 길이를 비교한다. 이에 맞춰 연결된 후속 차로열을 살피고 다음 구간의 선호 차로가 준비 거리 안에 들어오면 후보를 만든다. `onRouteFrame`의 `route_lane_change_activated` 인자로 외부 승인 상태를 전달할 수 있으며, 승인 입력이 없는 독립 재생에서는 후보를 실행하지 않는다. 원본 bag의 RTC 상태 출력을 독립 계산 입력으로 다시 넣지는 않았다.

원본 차로 변경 모듈의 `isValidPath`는 후보 경로점의 위치가 확장된 현재·목표 차로 안에 있는지 검사한다. 기존 planning-aa는 이 지점에서 차량 외곽 전체의 차로 포함을 요구해 후보를 거절했다. 차로 변경 후보에 한해 경로점 포함 검사를 적용했고, 출발·회피 등 다른 모듈의 차량 외곽 검사는 유지했다. 다만 bag의 외부 차로 변경 승인 시각과 원본 모듈 내부 상태가 독립 입력으로 재현되지 않았으므로, 원본이 109번 프레임에 발행한 차로 변경 경로의 형상·속도와 현재 독립 경로는 다르다. 독립 경로는 차량이 목표 차로로 들어가면 가장 가까운 route 차로로 전환하며, 이전 178~322번 프레임의 2m 초과 이탈은 0개가 됐다. 전체 최대 차량·독립 궤적 거리는 1.743m다.

원본 `JerkFilteredSmoother::apply`는 재표본화 결과가 한 점이면 QP 없이 초기 운동 상태를 출력하고, QP가 수렴하지 않으면 재표본화 결과를 후처리 경로로 남긴다. `VelocitySmootherNode::smoothVelocity`도 QP 실패 경고 뒤 정지점·최고 속도·후방 속도 처리를 계속한다. planning-aa는 이전에 `qp_result.solved == false`를 이유로 출력 전체를 버렸다. 해당 조기 종료를 제거하고 두 원본 분기를 반영했다. 이전에 비었던 323~330번과 425~458번의 42프레임을 포함해 459/459프레임에서 최종 스무더·validator 출력이 생겼다. 이 단계 직후 원본 출력이 기록된 454프레임의 차량 위치 계획 속도 절대 오차 중앙값/95백분위는 0.250/3.161m/s였다. 이는 최종 출력 연속성의 복구이며 속도 동등성의 증거는 아니다.

### IPC pedestrian 후반 재가속 차이의 입력 계약 수정

이전 재생의 300번 프레임은 원본 행동 속도 경로가 차량 위치에서 4.281m/s이고 첫 정지점은 약 29.21m 앞이지만, 독립 경로에는 약 0.36m 앞의 정지점이 생겼다. 속도 플러그인을 하나씩 제외한 진단에서 이 정지점은 신호등 모듈을 제외할 때만 사라졌다. bag의 신호 인식에는 규제 요소 `25004`만 있고 독립 경로의 해당 정지선은 `25005`다. 원본의 신호등 협조 상태는 300번 프레임에서 안전·활성이며, 원본 `TrafficLightModule::isStopSignal`은 `is_simulation`이 참이고 해당 신호 관측이 한 번도 없으면 통과한다. `BehaviorVelocityMapInput::is_simulation`을 신호등 코어에 전달하고 K-City 재생에 명시적으로 적용했다. 실제 환경의 기본값은 거짓으로 남겨 관측 없는 신호에서 정지한다. bag에 원본 노드의 런타임 파라미터 기록은 없으므로, 이 시뮬레이션 설정은 원본 출력·신호 입력·소스 분기에서 추론한 재생 가정이다.

횡단보도는 별개의 차이를 만들었다. 이전 330번 프레임에서 횡단보도 모듈만 제외하면 독립 행동 속도 경로의 차량 위치 속도는 원본처럼 11.11m/s, 첫 정지점은 독립/원본 22.466/22.468m가 된다. 원본 `crosswalk.param.yaml`의 `enable_rtc=false`와 `SceneModuleInterfaceWithRTC::setSafe`는 안전한 모듈을 자동 활성화한다. 독립 재생은 기존 활성 분기를 선택하지 않아 기본 정지 자세를 삽입했다. 입력에 `crosswalk_auto_activate_when_safe`를 추가하고 K-City 재생에서 명시적으로 설정했다. 기존 `crosswalk_enable_rtc` 필드는 호환성을 위해 유지했다.

두 설정을 함께 적용한 300·330·380번 프레임의 차량 위치 최종 계획 속도는 원본 `1.265/2.848/2.498m/s`, 독립 `1.206/2.991/2.066m/s`다. 28~40초 재가속 구간 120프레임의 속도 절대 오차는 중앙값 0.124m/s, 최대 0.563m/s다. 454개 공통 프레임의 절대 속도 오차 중앙값/95백분위는 이전 `0.250/3.161m/s`에서 `0.146/2.329m/s`로 줄었다. HPC pedestrian2의 오차도 `0.234/3.164m/s`에서 `0.069/2.173m/s`로 줄었으며, 나머지 8개 시나리오의 표 값은 변하지 않았다. 10개 시나리오 모두 전체 프레임에서 최종 출력이 유지된다. 경로 전체 점별 동등성은 여전히 달성되지 않았다.

행동 경로의 점별 일치는 44/459프레임으로 변하지 않았다. 원본은 109번 프레임부터 차로 변경 경로와 시작 속도 약 4.281m/s를 발행하지만, 독립 재생에는 승인 명령의 시각이 없다. bag의 `/planning/cooperate_status/lane_change_left`는 모듈이 계산한 협조 **출력**이므로 독립 입력으로 되먹이지 않았다. `onRouteFrame`은 외부 승인 상태를 받을 수 있으나 재생 입력에는 없다. 원본 `LaneChangeInterface::planWaitingApproval`/`plan`, 후보 준비 속도, 승인 후 모듈 유지·종료 상태와 현재 단일 프레임 경로 재계산의 차이도 남는다. 승인 명령 또는 동일한 외부 상태 기록을 확보한 뒤 연속 상태·경로 형상을 비교해야 점별 동등성을 판단할 수 있다.

### 그래프 잔차로 찾은 최종 평활화 초기 상태 차이

기존 IPC pedestrian 그래프의 190~215번 프레임에서는 첫 정지점까지의 거리가 원본과 독립 계산에서 거의 같았다. 예를 들어 190번은 원본/독립 3.976/3.930m였지만 차량 위치 계획 속도는 2.408/4.464m/s였다. QP는 해당 프레임에서 정상 수렴했다. 따라서 정지점 삽입이나 QP 실패가 이 속도 고착의 직접 원인은 아니었다.

원본 `VelocitySmootherNode::calcProjectedTrajectoryPointFromEgo`는 이전 내부 출력 궤적에서 거리·방향의 완화 조건으로 선분을 고른 뒤 **차량 위치를 투영하고 속도·가속도를 보간**한 값을 다음 계산의 초기 상태로 쓴다. 독립 종단 코어는 가장 가까운 **점 하나**의 값을 사용했다. `PlanningFinalPipelineCore`에서 원본의 선분 선택·투영 결과를 사용하도록 바꾸고 보간·겹친 경로의 방향 선택 검증을 추가했다. 이 수정에는 bag의 속도 값이나 프레임 조건을 넣지 않았다.

IPC pedestrian을 전체 459프레임 재생한 결과, 205번의 독립 계획 속도는 4.464→1.404m/s(원본 1.109m/s), 215번은 4.464→0.121m/s(원본 0.015m/s)로 줄었다. 원본 최종 출력과 대응되는 454프레임의 절대 속도 오차 중앙값/95백분위는 0.146/2.329→0.023/1.112m/s다. 다만 150번은 4.464→5.250m/s(원본 4.248m/s)로 오차가 늘었다. 전체 구간의 개선만으로 모든 프레임의 동등성을 주장할 수 없다.

갱신된 그래프에서 남은 주요 오차는 약 10~19초(첫 재생 수신 시각 기준) 차로 변경 구간의 독립 속도 과대 계획이다. 170번 프레임의 행동 경로는 원본/독립 시작 속도가 4.281/11.111m/s이고, 행동 속도 단계 첫 정지점도 차량에서 10.57/16.40m 떨어져 있다. 정지점이 비슷해진 190번 이후에도 앞 구간의 다른 경로·속도 이력이 초기 평활화 상태에 영향을 준다. 원본 차로 변경의 승인 명령과 내부 모듈 상태가 bag 입력에 없으므로, 원본의 중간 출력을 되먹이지 않는 현재 재생만으로 이 구간의 남은 차이를 제거하거나 행동 경로 동등성을 입증할 수 없다.

같은 코어 변경을 적용해 10개 bag을 모두 다시 재생했다. 이 시점에 8개 시나리오에서는 속도 절대 오차 중앙값이 줄었지만 HPC blocking의 중앙값/95백분위는 0.274/2.671→0.800/3.131m/s, HPC scurve는 0.215/1.402→0.802/4.747m/s로 커졌다. IPC cutinout은 중앙값이 줄었으나 95백분위는 1.671→2.726m/s로 늘었다. 당시 blocking 그래프는 약 30초 이후 독립 최종 계획이 0m/s에 머물렀고, scurve 그래프는 원본이 멈추는 구간에서 독립 경로의 첫 0m/s 점이 약 30m 앞에 남았다. 이후 blocking의 외부 제한 적용 방식은 수정했으며 현재 수치는 위 표를 따른다. 이 단계가 모든 시나리오의 동등성을 개선했다고 해석해서는 안 된다.

### 전체 재생 재검증과 최대 오차 S자 시나리오

같은 10개 bag을 다시 재생한 뒤 95백분위 오차가 가장 큰 HPC S자(이전 4.747m/s)를 우선 조사했다. 170번 프레임은 행동 경로·행동 속도·Elastic Band·경로 최적화·동작 속도 단계의 첫 정지점이 원본과 거의 같지만, 차로 주행 단계에서 원본은 차량 9.89m 앞에 정지점을 넣고 독립 계산은 넣지 않았다. 원본 `ObstacleCruisePlannerNode`의 정지·순항 객체 처리가 이 단계에 해당한다.

종전 시나리오 그래프 재생기는 인식 객체를 행동 속도 계산에는 전달하면서 종단 장애물 순항 후보에는 전달하지 않았다. `run_planning_pipeline_scenario_plots.py`의 전체 재생에 `--with-cruise-candidates`를 추가해 기존 후보 코어에도 같은 독립 입력을 전달했다. S자 170번 프레임의 독립 최종 첫 정지점은 36.11→11.89m(원본 9.89m), 계획 속도는 7.009→3.747m/s(원본 3.507m/s)로 바뀌었다. 전체 749개 대응 프레임의 절대 속도 오차 중앙값/95백분위는 이 단계에서 0.802/4.747→0.250/4.559m/s였다. 이후 순항 속도 제한도 종단에 연결한 4m 마진 재생의 S자 결과는 0.250/2.476m/s였고, 당시 6m 마진 재생은 0.250/1.903m/s였다. 10개 시나리오 모두 전체 프레임에서 최종 출력이 유지됐으며 최신 표와 기본 CSV·PNG에는 두 연결과 외부 제한점 삽입 수정이 적용됐다.

입력을 연결한 첫 전체 재생에서는 HPC blocking의 차로 변경 안전 검사에 유효하지 않은 인식 다각형이 도달해 재생 프로세스가 종료됐다. 원본 차로 변경 후보 안전 판정의 의미에 맞춰 이 경우 해당 후보를 안전하지 않은 것으로 처리하고 다음 계산을 계속하도록 했다. 수정 뒤 blocking 573프레임을 포함한 전체 재생이 완료됐으며, 이전 CSV를 재사용하지 않고 표·그래프를 다시 생성했다.

400·500번 프레임에서는 원본 차로 주행 경로의 정지점이 차량에서 약 10.82·16.10m 앞에 있지만 독립 계산의 정지 후보는 0개다. 기록 객체와 원본 정지 표식은 같은 차량 ID `ad879cf7`을 가리키며, 객체 속도는 각각 약 1.95·2.97m/s다. 기준 decision launch의 내부 객체 순항 전환 설정은 정지→순항 1.5m/s, 순항→정지 1.0m/s이고, 원본 패키지 YAML에는 별도 값 3.5/3.0m/s가 실제로 존재한다. 이 전환값을 `CruiseCandidateParameters`에서 선택 가능하게 이관하고 패키지 값을 **별도 민감도 실험**으로 재생했다. 이 실험에는 원본의 기록된 `max_velocity` 출력을 넣었으므로 독립 재생 결과가 아니다. 최신 종단 코어로 다시 그린 실험의 S자 속도 오차 중앙값/95백분위는 0.191/2.635m/s이며, 400번 정지점은 12.70m로 원본 10.90m에 가까워진다. 실험 [CSV](data/planning_aa_vs_autoware_scurve_hpc_package_hysteresis.csv)는 기본 결과와 분리했다.

bag에는 기록 당시의 파라미터 덤프가 없어 패키지 전환값이 실제 적용됐다고 확정할 수 없다. 또한 478번 이후에는 패키지 값을 적용해도 정지 누락이 남고, 기존 [콜백 경계 대조](obstacle_cruise_callback_boundary_20261010.md)에서 기록 당시 원본 출력과 현재 원본 실행 이미지의 정지 활성 자체가 일부 다름을 확인했다. 다음 비교 대상은 객체 메시지의 실제 polling 시각·ID, 원본 실행 파라미터, 미래 객체 충돌 분류 상태다. 그래프의 절대 오차만 줄이도록 객체 분류 임계값을 고정해서는 동등성을 입증할 수 없다.

### 외부 속도 제한과 최종 스무더 재검증

HPC cutinout의 212번 프레임에서 원본 차로 주행과 독립 차로 주행은 모두 차량 위치에서 11.111m/s였지만, 이전 독립 최종 계획은 0m/s, 원본은 10.164m/s였다. bag의 `/planning/scenario_planning/max_velocity`는 이때 약 4.81m/s로 내려간다. 이전 종단 코어는 이 값을 경로 전체의 즉시 제한과 최종 출력 제한에 모두 사용했다. 원본 `VelocitySmootherNode::calcExternalVelocityLimit`와 `applyExternalVelocityLimit`는 이전 출력의 속도·가속도 및 저크·감속 제약으로 제한 적용 거리를 구하고, 해당 거리의 경로점부터 제한한다. 최종 출력 상한에는 노드 설정값을 따로 사용한다. 이 상태와 거리 계산을 이관하고, 원본의 `calcInitialMotion`처럼 초기 운동 상태를 횡가속도 제한 전에 선택하도록 순서를 맞췄다.

다만 해당 `max_velocity`는 원본 장애물 순항 planner의 **출력**이다. 이 값을 다시 넣은 별도 진단에서 HPC cutinout 212번의 원본/독립 차량 위치 계획 속도는 10.164/10.213m/s, 첫 0m/s 점까지의 거리는 106.20/105.56m다. [HPC cutinout 기록 제한 CSV](data/planning_aa_vs_autoware_cutinout_hpc_recorded_limit.csv)는 기본 독립 재생과 분리했다. 이는 최종 스무더의 **조건부** 검증이며 route부터의 독립 동등성 증거가 아니다. 기록된 제한 메시지의 CDR에는 최소 가속도·최대/최소 저크 세 값만 있고 로컬 checkout의 `VelocityLimitConstraints.msg`에는 최대 가속도도 있다. 따라서 이 기록에서 최대 가속도 요청 분기는 확인할 수 없다.

외부 제한 메시지가 전혀 없는 기록에는 해당 제한점 삽입을 하지 않는다. 원본 노드는 기본 노드 상한만 있을 때에도 0m 거리의 제한점을 삽입하지만, 현재 ROS 비의존 경로에서 이를 그대로 재현하면 곡선의 경로점 배치가 달라져 HPC rotary와 두 정지선 bag의 최종 속도 오차가 커졌다. 이 생략은 제한값 자체가 노드 상한과 같은 경우에만 적용하며, 원본과의 경로점 동등성을 뜻하지 않는다. 삽입점의 원본 방향·겹침·가까운 선분 선택을 추가 대조할 필요가 있다.

HPC blocking의 약 25~30초 차이는 최종 스무더보다 앞선 행동 경로에서 시작된다. 250번 프레임의 독립 행동 경로는 차로 `36` 끝의 정지점이 차량 36.25m 앞이고 원본은 차로 `15850`, `15910`까지 이어져 약 64.99m 앞에서 멈춘다. 기본 독립 최종 계획의 275번 프레임 속도도 원본 3.243m/s, 독립 7.011m/s다. bag의 `/planning/cooperate_status/lane_change_left`에서는 약 13.4초에 활성 명령이 나타나고, 원본 행동 경로에는 16.5초부터 목표 차로가 들어간다. 이 협조 상태는 원본 모듈의 **출력**이므로 독립 재생 입력으로 되먹이지 않았다. 외부 승인 명령의 원본 입력 시각 없이 이 구간의 행동 경로·최종 속도 동등성을 주장할 수 없다.

### 계산된 순항 제한의 종단 연결

원본 `ObstacleCruisePlannerNode`는 충돌 후보의 첫 충돌점과 자차 앞 길이로 객체 거리를 구해 `PIDBasedPlanner`의 제한값을 만들고, 대상이 사라지면 `obstacle_cruise_planner.cruise` 제한을 한 번 해제한다. planning-aa의 기존 객체 후보·PID·제한 선택 코어를 연결했다. 후보 단계가 첫 충돌점까지의 거리와 경로 방향 객체 속도를 PID에 전달하고, 새 제한과 해제 이벤트를 `PlanningPipelineMapResult::selected_velocity_limit`로 반환한다. `applySelectedVelocityLimit`는 이 이벤트를 최종 스무더 프레임의 속도·가속도·저크 제한 입력으로 옮긴다. 기본 종단 재생은 원본 Planning 출력을 다시 읽지 않고 이 계산값을 사용한다. 원본 `max_velocity`를 넣는 `--with-recorded-external-limit`는 별도 최종 스무더 진단이며, 이 모드에서는 계산된 제한을 최종 프레임에 중복 적용하지 않는다.

이번 변경 전/후의 HPC cutinout 속도 오차 중앙값/95백분위는 1.399/4.754→0.098/1.528m/s, IPC cutinout은 0.461/4.452→0.143/1.009m/s다. HPC S자의 95백분위도 4.559→2.476m/s로 줄었다. 원본 제한을 넣은 기존 조건부 진단의 HPC/IPC cutinout 오차는 각각 0.039/2.320, 0.040/2.112m/s다. HPC cutinout 212번의 독립 속도는 8.560m/s로 원본 10.164m/s보다 낮다. 190번에는 독립 후보 1개와 9.919m/s 제한이 있지만, 원본 선택 제한 출력은 약 201번부터 기록되어 있다. 212번 제한값도 독립 5.517m/s, 원본 기록 4.809m/s다. 원본 객체 선택 시각과 입력 경로·인식 짝, 충돌 다각형을 추가 대조해야 한다. 이 차이를 보정하려고 bag 전용 지연값은 넣지 않았다.

위 문단의 수치는 **순항 마진 4m의 이전 재생**이다. 현재 K-City 재생은 기록에서 확인한 6m를 사용하며 표의 HPC/IPC cutinout 오차는 각각 0.026/1.757, 0.015/1.135m/s다. HPC S자의 95백분위는 1.741m/s다. 6m는 원본 실행 RSS 거리를 맞추지만 조기 후보로 인한 HPC cutinout의 큰 속도 차이를 해소하지 않는다. [후보 경계 감사](obstacle_cruise_candidate_boundary_20261011.md)에서 사용한 원본 경로 최적화 출력은 실제 순항 노드 입력보다 한 단계 이르므로 원본과의 후보 시작 비교 근거가 아니다. 실제 입력인 동작 속도 궤적을 사용한 [순항 콜백 스냅샷 감사](obstacle_cruise_callback_snapshot_20261011.md)는 현재 원본 노드 이미지와 후보 활성 집합이 일치하고 보유 기록과는 다름을 보여 준다. 당시 콜백 입력 짝·실행 설정 확인이 남아 있다.

이 표는 점 수 차이 또는 점별 1mm·0.001m/s 초과를 **처음** 발견한 위치다. 작은 절단 경계 차이도 행동 경로로 잡히므로 속도 오차의 크기나 원인 비중을 뜻하지 않는다. 단계별 원본 메시지는 비교에만 사용했고 정확한 원본 callback ID의 동일성은 확인되지 않았다.

HPC blocking 기본 573프레임의 첫 차이는 모두 행동 경로다. 250번은 독립 행동 경로 24점, 원본 65점이고 첫 정지점은 차량 36.25/64.99m 앞이다. 320번은 13/54점, 첫 정지점 13.31/41.90m다. 원본 `LaneChangeInterface::updateData`/`NormalLaneChange::hasFinishedLaneChange`에 맞춰 승인된 경로의 연속 유지·종료 조건을 연결했다. 또한 원본 `getExpandedLanelet`의 `offsetNoThrow`로 변경 방향의 목표 차로 바깥쪽만 1m 확장한다. 기존 단순 법선 이동과 원본 방식의 확장 경계 모두 이 곡선 구간에서 Boost의 엄격한 `is_valid` 검사를 통과하지 않았다. 독립 코어의 이 조기 검사 때문에 가상 승인 구간의 후보 350개가 충돌 검사 전에 모두 거부됐다. 원본 객체 분류에는 해당 조기 유효성 검사가 없으므로 제거했다. 수정 후 가상의 170~350번 승인 입력을 준 재생에서는 안전 후보가 81프레임, 실제 차로 변경 경로도 81프레임 생성됐다. 320번 최종 속도는 원본 1.858m/s, 기본 독립 5.138m/s, 가상 승인 독립 2.396m/s다. 조건부 573프레임의 속도 오차 중앙값/95백분위는 기본 0.146/3.707에서 0.340/2.957m/s로 바뀌었다. 이 입력은 기록된 원본 명령이 아니므로 기본 그래프·표에 반영하지 않았다. 기본 독립 재생의 최종 점 수·차량 위치 속도·첫 정지 거리는 변경 전후 573프레임 모두 같다.

같은 진단을 IPC 보행자 bag에도 적용했을 때 가상의 100~210번 승인 구간에서 안전 후보·차로 변경 경로가 75프레임 생성됐다. 그러나 가상 승인 재생의 속도 오차 중앙값/95백분위는 0.020/1.159m/s로, 기본 표의 0.020/1.124m/s보다 후반 오차가 커졌다. 승인 시각 추정만으로 점별 동등성을 주장하거나 한 bag의 속도 오차에 맞춰 조정할 수 없다.

HPC S자의 첫 차이는 행동 경로 622프레임, Elastic Band 110프레임, 경로 최적화 20프레임이며 1프레임은 원본 단계 대응이 부족하다. 630번은 행동 경로 64/64점, 경로 최적화·동작 속도 242/242점이고 각 단계의 차량 위치 속도도 11.111m/s로 같다. 반면 최종 속도는 독립 2.363m/s, 원본 7.076m/s다. 기록된 원본 중간 경로와 원본 이전 스무더 출력을 넣은 **조건부** 독립 스무더는 390~419번 공통 경로의 최대 속도 차이 0.012m/s, 620~649번 0.187m/s다. 따라서 630번 종단의 4.713m/s 차이는 스무더 식 하나보다 입력 경로의 형상·이전 상태·콜백 짝의 누적 차이에서 먼저 추적해야 한다. 원본 당시 파라미터와 정확한 콜백 ID는 현재 기록에 없다.

원본 `VelocitySmootherNode::calcTrajectoryVelocity`/`extractPathAroundIndex`는 경로를 기본 앞 200m·뒤 5m로 절단한 다음 외부 속도 제한과 정지 접근 처리를 한다. 독립 종단 코어의 순서를 이와 같게 수정하고 긴 경로의 후방 절단을 단위 검사했다. 당시 S자 전체 753프레임의 차량 위치 속도 오차 중앙값/95백분위는 수정 전후 모두 0.250/1.903m/s였고 630번 독립 속도도 2.363m/s로 같았다. 이 순서 차이는 630번의 주원인이 아니었다. 이후 외부 제한점 삽입 기준을 원본에 맞춘 최신 630번 독립 속도는 7.090m/s다. 원본/독립 시나리오 선택 경로의 점별 형상·이전 스무더 상태와 실제 원본 콜백 입력 짝의 동등성은 아직 확인되지 않았다.

원본 `calcExternalVelocityLimit`의 저속 출발 때 새 제한을 즉시 적용하는 분기와, 정지 상태에서 0m/s 외부 제한 거리를 지우는 분기도 반영했다. 같은 S자 전체 재생에서는 두 분기 수정 전후 계획 속도가 달라진 프레임이 없었다. 동작 속도 plugin의 기본 적용 순서와 동적 적재·해제를 원본 manager에 맞춘 뒤 10개 시나리오의 기본 CSV·그림을 다시 생성했다. 이 단계의 6,085개 출력·6,047개 비교 프레임에서 blocking·S자 오차는 기존과 같고 IPC 정지선 중앙 오차는 소수 셋째 자리 반올림 시 0.003에서 0.002m/s로 바뀌었다. 당시 0.5m/s 이내 비율은 83.0%였으며, 이후 수정까지 포함한 최신 집계는 위의 85.1%다.

추가 단계 감사에서 S자 390번은 원본 차로 주행의 첫 정지점이 차량 10.266m 앞이고 독립 경로에는 해당 정지점이 없어 약 189.725m 앞 종점만 정지점이다. 630번은 차로 주행의 양쪽 점 수가 242개이고 첫 정지 거리도 독립/원본 114.269/114.269m로 가깝지만 최종 스무더 속도는 2.363/7.076m/s다. 이 결과는 중간 390번의 정지·순항 분기가 만든 이전 상태 차이와 630번 입력 형상·콜백 짝을 함께 검사해야 함을 보여 준다. 보유 기록의 S자 정지 활성과 현재 원본 이미지·planning-aa의 조건부 활성은 크게 다른 반면, 현재 이미지와 planning-aa는 정지 25/25프레임이 일치한다([콜백 입력 감사](obstacle_cruise_callback_snapshot_20261011.md)). 따라서 보유 기록에 맞춘 임의 임계값 변경은 적용하지 않았다. 별도로 기본 동작 속도 plugin의 결과 적용 순서는 원본 launch의 장애물 제한 → 동적 정지 순서로 정리했다. 두 plugin을 모두 사용하는 입력에서의 종단 수치 동등성은 아직 확인되지 않았다.

원본 동작 속도 launch의 첫 plugin인 OutOfLane은 별도 `PlanningOutOfLaneInput`에 콜백 당시 예측 객체·적색 신호와 최소 제동 호길이 또는 속도·가속도·평활화 제한을 명시하면 지도 후보, 이전 결정 상태, 정지/감속 결과까지 종단에 연결된다. 후자의 최소 호길이 계산은 원본 `PlannerData::calculate_min_deceleration_distance`와 이전 감속점 규칙을 따른다. 도착시각은 선택적으로 원본 `motion_utils::calculate_time_from_start`처럼 0.5m 재표본화 후 최근접 자차 선분 뒤에서 1m/s 하한으로 적분한다. 실제 bag 재생에는 원본 콜백의 입력 짝과 당시 평활화 제한이 확보되지 않아 새 입력을 공급하지 않았다. 기록된 경로·객체를 넣는 기존 조건부 `out_of_lane_rosbag_replay.py`는 HPC S자 753프레임, HPC blocking 580프레임, IPC 보행자 460프레임에서 각각 후보 0개·원본 동작 속도 출력 변경 0프레임이었다. 이는 세 기록에서 해당 분기가 차이를 만든 증거가 없다는 뜻이며 종단 동등성 증명은 아니다. [콜백·제동 감사](motion_velocity_callback_audit_20261011.md)는 원본 header 대응, polling 입력 짝의 불확실성, blocking·S자의 첫 큰 차이를 별도로 정리한다.
