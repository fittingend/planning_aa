# 행동 경로 기준선과 콜백 입력 시각 감사 (2026-10-11)

## 원본 계산 경계

원본 `BehaviorPathPlannerNode::run`은 AUTONOMOUS이면서 제어가 켜진 경우가 아니고 재경로를 막는 승인 모듈도 없으면 현재 route lanelet을 다시 고른다. `PlannerManager::run`은 현재 차로를 갱신하고 `getReferencePath` 결과를 `root_reference_path` 표식으로 발행한 다음 행동 모듈을 실행한다. `getReferencePath`는 차량 위치를 **현재 차로 중심선에 투영**하고, 후방 설정값에 10m를 더해 원시 중심선을 자른 뒤 재표본화하며, 마지막으로 후방 설정값과 입력 간격을 기준으로 다시 자른다. 코드 위치: 원본 `behavior_path_planner_node.cpp:364`, `planner_manager.cpp:116,236,271`, 공통 `path_utils.cpp:453`, `utils.cpp:976`.

따라서 `root_reference_path` 표식은 행동 모듈 이전의 계산을 가리킨다. 다만 표식 **수신 시각**은 콜백 내부에서 odometry 등을 실제로 읽은 시각이나 메시지 ID가 아니다.

## 보유 rosbag 관찰

- HPC S자: 처음 129프레임의 root 표식은 독립 경로와 거의 같은 좌표 격자를 사용한다. 130번부터 원본 격자는 콜백마다 이동하지만 기본 독립 경로는 몇 콜백 동안 같은 격자를 유지한다. 행동 경로의 점별 일치는 첫 160프레임 중 128프레임이다.
- HPC blocking: 320번의 첫 큰 종단 차이는 행동 경로에서 시작한다. 독립 13점과 기록 원본 54점의 차이는 이후 속도 계산만 바꿔 해결할 수 없다. RTC **상태 출력**은 있지만 승인 **명령 시각**은 없다.

- 원본 알고리즘을 따라 원시 중심선을 먼저 자르는 실험 경로에서 S자 130번 이후 기준선 잔차는 약 0.18m다. `root_reference_path` 수신 시각을 입력 조회 상한으로 사용하면 해당 잔차는 약 0.10m다. 이 시계는 원본 콜백 입력 ID를 복원하지 않는다.
- root 표식과 행동 경로 출력의 기록 수신 시각 사이에 새 odometry가 들어온 프레임은 S자 160개 중 132개, blocking 351개 중 224개다. 표식을 현재 행동 콜백에 대응시킬 수 있는 것은 각각 135/160, 330/351프레임이며 나머지는 행동 경로 수신 시각을 사용한다. 따라서 행동 경로 출력 시각에서 최신 입력을 고르는 기본 재생에는 실제 원본 입력과 다른 메시지를 선택할 여지가 있다.
- blocking에서는 차량이 정지한 초기 구간에도 원시 절단 실험과 원본 표식 사이에 약 0.1m의 일정한 격자 차이가 남는다. 입력 시각만으로 전부 설명되지 않는다. 보유 K-City 지도 해당 차로의 중심선 높이는 0m이고 waypoint 속성은 없어, 이 두 항목도 잔차의 원인으로 확인되지 않았다.

원본 `motion_utils::cropBackwardPoints`가 후방 경계를 넘은 점 `i`부터 유지하는 것을 확인해 기본 독립 경로의 `i-1`을 `i`로만 바꿔 전체 blocking·S자·IPC 정지선을 진단 재생했다. blocking의 속도 오차 중앙값/95백분위는 0.1445/3.7067→0.1445/3.7066m/s로 사실상 같고, S자는 0.0356/1.7413→0.0349/1.7413m/s였다. 그러나 S자의 첫 차이가 행동 경로인 프레임은 622→657, IPC 정지선은 498→574로 늘었다. 이는 원본 절단 인덱스 하나를 이미 다른 원시 중심선 표본화 격자·자차 콜백 자세에 적용한 결과다. 단독 변경은 기본값으로 채택하지 않았고, 원본식 절단은 기존 `--experimental-route-sequence-clip` 진단 경로에 남겼다.

원본 `getReferencePath`가 사용하는 `findFirstNearestSegmentIndexWithSoftConstraints`의 점 선택·거리/방향 조건·대체 탐색을 진단 경로의 마지막 절단에도 연결했다. 기준 launch의 최근접 거리 3m, 방향 1.046rad을 사용하며 기본 재생 경로는 바꾸지 않는다. 첫 160프레임의 root 표식 좌표가 1mm 이내이고 점 수도 같은 경우는 다음과 같다. 분모는 대응 표식이 있는 프레임 수다.

마지막 조건의 수정 전 첫 160프레임 최종 속도 절대 오차 중앙값/95백분위는 blocking 0.0035/0.0971m/s, S자 0.0004/0.0611m/s였다. 재표본화 수정은 기본 10개 시나리오의 종단 속도 지표를 거의 바꾸지 않았다. 진단 경로에서 S자는 행동 경로·행동 속도 점별 일치가 각각 158/160프레임이며, 첫 프레임의 차이는 이미 Elastic Band 점 수 482/484에서 시작한다. 따라서 이 초기 구간은 기준선 다음의 이전 최적화 상태·재계획 및 연결 단계가 조사 대상이다. 원본 기본 YAML의 후방 길이는 5m이고 기록 당시 파라미터 덤프는 없다. 7.1m는 이 구간의 **조건부 정합값**일 뿐 실행 설정이나 다른 시나리오의 원본 동등성을 증명하지 않는다. 5m 진단이 오히려 S자 일치를 줄이는 만큼 절단 전 경로 격자와 실제 입력 자세를 함께 확인해야 한다.

## 설정 가설을 다른 시나리오에 대조

원본 기본 YAML의 후방 경로 길이는 5m다. 두 HPC bag의 첫 계산 잔차가 공통으로 약 0.1m여서, 원본의 중심선 투영과 원시 경로 절단 순서를 적용한 **진단 옵션**에서 후방 길이 7.1m를 시험했다. S자 160프레임 중 root 표식 좌표가 수치상 같은 구간은 130~155번을 포함하며 행동 경로 점별 일치는 128→157프레임이다. blocking에서도 정차 중인 25~45번과 130~155번의 root 표식 좌표가 수치상 일치했다. 그러나 전체 bag에서는 아래처럼 뒤 구간의 상태·모듈 경로 차이가 계속된다.

아래 root 표식 수치는 재표본화 근접점 처리까지 적용한 전체 진단 결과다. 진단 후방 길이 7.1m는 기록 당시 설정으로 확인되지 않았다. 최신 기본 S자 최종 속도 중앙 오차는 0.036m/s다. 390번 정지 후보와 기록 당시 파라미터도 여전히 미확인이다.

| 진단 재생 | root 표식 좌표 일치 / 점 수 차이 / 수치 차이 / 표식 없음 |
| --- | ---: |
| HPC S자 753프레임 | 540 / 24 / 164 / 25 |

blocking의 남은 root 점 수 차이 171프레임 중 가장 긴 연속 구간은 327~409번(83프레임)으로 차로 변경 구간에 겹친다. S자는 root 좌표 차이 164프레임이 주로 후반부에 있으며 가장 긴 연속 구간은 533~549번(17프레임)이다. 이 분포 때문에 초기 재표본화 수정만으로 후반 종단 오차가 줄지 않는다. 정확한 원본 차로 변경 승인 명령 시각과 각 노드가 읽은 odometry·경로 ID가 없으므로 해당 구간의 남은 root 차이를 원본 계산식 오류로 단정하지 않는다.

같은 전체 진단에서 행동 경로가 첫 차이인 프레임은 blocking 420/573, S자 238/752다. S자는 나머지 중 Elastic Band 180, 경로 최적화 334프레임에서 첫 차이가 난다. 초기 0번 프레임은 행동 경로와 행동 속도가 원본과 점별로 같지만 Elastic Band는 독립 482점/원본 484점이며, 독립 시작점 `(2597.895, 24259.788)`은 원본 `(2597.911, 24258.788)`보다 경로상 약 1m 뒤다. 종점은 같다. 원본 `EBPathSmoother::smoothTrajectory`는 `motion_utils::cropPoints`로 전방·후방 절단 후 이전 최적화 경로의 고정점을 넣는다. bag에는 독립 재생의 첫 유효 입력보다 앞선 원본 출력이 Elastic Band 3개, 경로 최적화 7개, 동작 속도 19개 있다. 첫 odometry 수신은 첫 원본 Elastic Band 출력보다 늦고, 첫 객체 입력은 세 번째 출력보다 늦다. 따라서 독립 재생을 첫 유효 프레임에서 새 상태로 시작하면 원본의 이전 최적화 상태를 복원할 수 없다. 이 기록은 시작점 차이가 이전 상태·재계획 경계에서 생겼을 가능성을 뒷받침하지만 실제 내부 상태값은 증명하지 않는다. 원본 출력 수신 시각에 최신인 odometry 위치 `(2597.592, 24264.435)`는 독립 재생에서 고른 위치와 같다. 원본 노드가 실제로 polling한 odometry ID와 실행 당시 `output_backward_traj_length`는 여전히 미확인이다. 패키지 YAML 기본값은 5m이며, 첫 출력에 맞춘 임의 후방 길이 조정은 적용하지 않았다.
| IPC 보행자 459프레임 | 199 / 252 / 8 / 0 | 0.020 / 1.124 → 0.017 / 1.126 |

7.1m가 여러 초기 구간의 기준선 좌표를 맞추지만, **기록 당시 설정값이라는 증거는 아니다.** 세 bag의 `/parameter_events`에는 메시지가 0개이고 런타임 파라미터 덤프도 없다. 동일한 2m 재표본화 격자를 다른 절단 시작점에서 만들 가능성도 남는다. 최종 속도 95백분위가 S자와 blocking에서 오히려 커져 기본 설정을 바꾸지 않았다. 원본 코드의 중심선 투영은 실험 경로에 반영했으며 기록에 맞춘 고정 오프셋은 넣지 않았다.

### S자 큰 속도 차이의 원인 분리

630번의 기본 종단 재생은 독립 2.363m/s, 원본 7.076m/s다. **원본식 원시 중심선 선행 절단만** 켜고 후방 길이 5m와 기존 행동 경로 수신 시각을 유지하면 독립 값은 7.088m/s다. 후방 길이 7.1m와 root 표식 입력 시계를 함께 쓰면 7.086m/s다. 따라서 이 프레임의 큰 차이는 7.1m 추정값이나 표식 시계가 없어도 원시 경로의 절단·재표본화 시작점과 이어진 상태를 원본 순서로 계산하면 거의 사라진다. 620~649번의 최종 속도 절대 오차 중앙값/95백분위는 기본 3.473/4.678m/s, 선행 절단·5m 진단 0.028/0.183m/s, 선행 절단·7.1m·표식 시계 진단 0.027/0.105m/s다.

390번에는 7.1m·표식 시계 진단에서 root 기준선, 행동 경로, 행동 속도의 점 수·차량 위치 속도와 첫 정지 거리가 원본과 맞는다. 경로 최적화와 동작 속도의 첫 정지 거리는 약 189.728m로 가깝지만, **차로 주행 출력**에서 독립 189.728m와 기록 원본 10.266m로 갈라진다. 순항 후보는 없었다. 이 구간의 390~419번 최종 속도 오차는 기본 중앙값/95백분위 1.131/1.244m/s에서 선행 절단·5m 진단 1.641/1.799m/s로 커진다. 전체 S자 95백분위가 악화된 주된 제한이며, 원본 기록 당시의 차로 주행 정지 선택 입력·설정과 현재 원본 이미지의 차이도 남는다.

기록 원본의 390·400·500번 `obstacle_cruise_planner/debug/marker`에는 `obstacles_to_stop`과 `stop_collision_points`가 각각 1개 있고 630번에는 둘 다 없다. 390번 표식의 장애물 위치는 약 (2567.161, 24321.151)m다. 원본 소스의 `StopPlanningDebugInfo` 필드 순서로 읽으면 해당 콜백의 정지 정보는 장애물 거리 약 15.88m, 속도 약 1.94m/s, 목표 거리 6m다. 즉 기록 당시 원본은 **장애물 정지 후보를 실제로 선택**했다. 행동 경로 수신 직전 인식 입력에도 같은 위치에서 0.18m 떨어진 CAR 객체가 있고, 수신 뒤 약 44ms의 다음 객체 메시지에는 0.05m 떨어진 CAR 객체가 있다. 후보가 없어진 이유를 객체 부재만으로 설명할 수 없다.

독립 재생의 순항 입력 조회 시계를 원본 경로 최적화 출력 수신 시각과 동작 속도 출력 수신 시각으로 각각 늦춰도 390번의 후보 수는 0이고 정지점은 삽입되지 않았다. 당시 원본의 정확한 polling 반환 ID와 충돌점 생성·후보 필터 파라미터는 여전히 불명확하다. 다음 비교는 해당 객체의 예측 경로, footprint, 충돌점과 정지 후보 거절 조건을 원본 소스와 동일한 입력 짝으로 확인해야 한다.

후보 선택 이후에도 원본 `PlannerInterface`는 `LongitudinalInfo::safe_distance_margin`을 정지 거리 계산에 사용한다. 독립 후보 코어의 4m 고정값을 제거하고 기존 순항 안전거리 입력을 정지 후보에도 전달하도록 수정했다. 6m 설정의 합성 정지 후보가 6m 여유를 내는 회귀 검사로 확인했다. 이 수정만으로는 390번의 **후보 0개** 문제가 해결되지 않는다.

### S자 정지 후보의 설정·미래 판정 분리

위의 390번 후보 0개는 원시 경로 선행 절단·표식 시계를 함께 사용한 진단 조건이다. 기본 재생에서는 이 CAR 객체가 **정지 대신 순항**으로 선택된다. 원본 패키지 YAML의 정지→순항/순항→정지 임계값 3.5/3.0m/s를 적용하고 원본 동작 속도 출력 수신 시각에 객체를 대응하면 390번의 정지 후보가 1개가 된다. 차로 주행 첫 정지점은 기록 10.266m, 독립 10.270m이고 최종 차량 위치 속도는 기록 1.380m/s, 독립 1.394m/s다. 앞 객체의 현재 외형과 정지 교점이 가까운 만큼 속도 전환 설정과 객체 조회 시각이 이 프레임의 큰 차이에 관여한다. 단, 기준 Obigo launch의 임계값은 1.5/1.0m/s이며 기록 당시 런타임 값은 없다.

같은 조건에서 478번부터 독립 정지가 다시 빠진다. 500번에는 원본 기록의 객체·정지 충돌점 좌표가 각각 (2542.537, 24336.265)m, (2544.524, 24335.328)m다. 독립 계산도 현재 외형 충돌을 찾지만 차량 도착 예상 8.53초에서 1초를 뺀 시각의 최상위 예측 경로 자세가 약 (2524.482, 24346.052)m여서 미래 충돌이 없다고 판정한다. 원본 소스 `createStopObstacleForPredictedObject` 역시 현재 충돌 뒤 미래 자세를 검사해 사라진 객체를 제외한다. 보관된 **현재 원본 노드 재실행**은 478~535번에서 `intentionally_ignored_obstacles`를 출력하고 정지를 제외했지만, 기록 당시 bag에는 계속 정지 출력이 있다. [현재 원본 재실행 감사](obstacle_cruise_live_replay_20261010.md)의 같은 58프레임과 일치한다. 이 구간을 bag 결과만 맞추도록 코어에서 미래 검사를 제거할 근거는 없다.

외부 제한점 삽입을 원본에 맞춘 뒤 패키지 전환 임계값 3.5/3.0m/s와 원본 코드에 존재하는 충돌 시간 여유 10초를 **조건부**로 주고 동작 속도 출력 수신 시계에 순항 입력을 대응했다. S자 종단 속도의 중앙값/95백분위 오차는 0.013/0.201m/s, 749개 비교 프레임 모두 0.5m/s 이내다. 같은 조건을 10개 bag에 적용한 6,047개 대응 프레임의 0.5m/s 이내 비율은 기본 85.1%에서 91.1%로 바뀐다. 그러나 blocking의 320번 첫 행동 경로 차이는 그대로이고 IPC 끼어들기의 95백분위 오차는 증가한다. 기준 launch와 패키지 YAML의 충돌 시간 여유는 모두 1초이고 `/parameter_events`에도 기록이 없다. 10초가 당시 설정값이거나 현재 원본과 동등하다고 판정하지 않으며, 기본 설정과 시나리오 그래프는 바꾸지 않았다.

| 조건부 재생 대상 | 기본→조건부 0.5m/s 이내 | 기본→조건부 95백분위 오차 (m/s) |
| --- | ---: | ---: |
| HPC S자 | 71.7→100.0% | 1.741→0.201 |
| HPC blocking | 59.9→65.3% | 3.707→3.649 |
| HPC 돌발진입 | 95.7→100.0% | 0.418→0.082 |
| HPC 보행자2 | 86.7→86.9% | 1.059→1.042 |
| IPC 끼어들기 | 85.9→91.4% | 1.135→1.208 |
| 10개 전체 | 85.1→91.1% | 1.538→1.122 |

전환 임계값은 재생기의 `--cruise-stop-to-cruise-speed`와 `--cruise-cruise-to-stop-speed`로 각각 명시할 수도 있다. 기록 당시 값을 알아낸 것은 아니며, 기준 launch(1.5/1.0m/s)와 패키지 YAML(3.5/3.0m/s)을 같은 계산 경로에서 시험하는 옵션이다.

### S자 후반의 최종 평활화 경계

패키지 임계값·10초 충돌 여유·원본식 원시 경로 절단을 함께 켠 **삽입점 수정 전** 조건부 재생은 605~612번에 원본과 비슷한 첫 정지점(독립 약 61~64m, 기록 약 61~64m)을 만들었다. 613번의 **시나리오 선택 경로 첫 정지점은 독립/기록 모두 약 126.2m**지만 최종 평활화 첫 정지점은 독립 11.8m, 기록 64.3m로 갈라졌다. 독립 코어를 추적하면 외부 제한·횡가속도·조향 제한 후 입력과 QP 최적화 입력의 첫 정지는 여전히 약 126.2m였다. ProxQP 결과에서 9번째 점의 속도가 0으로 내려갔다가 10번째 점부터 다시 양수가 됐고, 그 한 프레임의 내부 궤적이 다음 콜백 초기 상태로 들어가 615~630번 감속 차이가 이어졌다. 당시 630번 속도는 독립 3.59m/s, 기록 7.08m/s였다.

원본 `JerkFilteredSmoother::apply`도 QP 변수인 제곱속도 `b`가 음수가 될 수 있게 허용하고 결과를 `sqrt(max(b, 0))`로 바꾼다. 따라서 0점을 사후 제거하는 수정은 원본 이관이 아니다. 실제 원인은 QP 이전의 **외부 제한점 위치**였다. 원본 `applyExternalVelocityLimit`는 `findFirstNearestSegmentIndexWithSoftConstraints`가 선택한 선분의 **시작점**에서 제한 거리를 재고 `insertTargetPoint`는 1mm 이내 중복점 판정과 앞 점의 속도·선분 방향을 쓴다. 독립 코어는 차량의 경로 투영점에서 거리를 재고 새 점의 속도를 보간했다. 이 계산을 원본 방식으로 바꾼 뒤 같은 결합 진단의 613번 첫 정지는 독립 63.9m/기록 64.3m, 630번 속도는 독립 7.108m/s/기록 7.076m/s다. 749개 비교 프레임이 모두 0.5m/s 이내이고 95백분위 오차는 0.205m/s다. 원본 평활화 raw·필터·QP 입력 디버그 궤적은 기록되지 않아 QP 입력의 점별 동등성은 여전히 미확인이다.

원본 `VelocitySmootherNode::applyExternalVelocityLimit`는 새 제한 메시지가 없어도 매 궤적에 호출된다. planning-aa에서도 동일하게 호출하고 제한점의 기준 선분·새 점 값을 맞췄다. S자 기본 749개 비교 프레임의 중앙값/95백분위 오차는 0.054/1.903→0.036/1.741m/s, 0.5m/s 이내 비율은 66.5→71.7%로 바뀌었다. 기본 613번 첫 정지도 독립 63.9m/기록 64.3m, 630번 속도는 독립 7.090m/s/기록 7.076m/s다. 390번 정지 선택, 478~535번 기록 원본과 현재 원본의 판단 차이는 남는다.

원본식 절단은 코드에 선택적 진단 경로로 구현했다. 원본과의 초기 기준선 정합은 확인했으나 세 시나리오 전체의 최종 속도가 일관되게 나아지지는 않아 기본 재생에는 적용하지 않았다.

## 이어서 확인할 사항

1. 원본 행동 경로 콜백이 실제로 사용한 odometry·신호·객체의 메시지 ID와 런타임 후방 길이/재표본화 설정을 확보한다. 현 기록만으로 확정할 수 없다.
2. 승인 분기는 명령 시각이 확보될 때까지 조건부 합성 입력 결과와 실제 동등성을 분리한다.
3. 같은 콜백 입력·상태를 맞춘 뒤 root 표식, 행동 경로, Elastic Band, 최적화, 동작 속도, 차로 주행 정지 선택, 최종 스무더 순서로 첫 차이를 비교한다. 390번 정지 삽입은 패키지 임계값 진단에서 맞지만 실제 런타임 임계값이 미확인이다. 613·630번 종단 값은 제한점 삽입 수정으로 가까워졌으나 원본 QP 디버그 입력·이전 상태의 점별 동등성은 미확인이다.

재생 진단 옵션은 `tests/planning_pipeline_rosbag_replay.py --from-route --callback-clock recorded-behavior-receipt --input-snapshot-clock root-marker-receipt --experimental-route-sequence-clip`이다. root 표식은 시계와 비교 출력에만 사용하며 경로 점은 코어 입력으로 다시 주입하지 않는다.
